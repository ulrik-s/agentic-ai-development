Part 1

LLMs — getting on the same page

Snabbt genom det här. De flesta i rummet har använt ChatGPT eller Claude. Men det är värt att vara explicit om vad det faktiskt är — för det förklarar både vad det är bra på och var det kommer fela.

What an LLM actually is

  • A function: tokens → next token probability
  • Trained on enormous corpora of text + code
  • No memory between calls. No database lookup. No internet (by default).
  • It is not retrieving answers — it is generating them
If you remember one thing: it is a very fast, very fluent pattern completer.
Det viktiga: modellen "vet" ingenting. Den genererar det mest sannolika nästa token givet kontexten. När den verkar minnas något — så har den fått det matat till sig i prompten eller via ett verktyg. Det finns ingen "minnesbank" inuti. Det här förklarar varför den kan hitta på (hallucinera): att hitta på och att svara rätt är samma operation för modellen. Den vet inte skillnaden.

Tokens, context, prediction

Token

A chunk of text (~4 chars). The model sees and emits tokens, not characters or words.

Context window

Everything the model can "see" right now — prompt + conversation + tool outputs. Modern models: 200k–1M tokens.

Prediction loop

while not done:
    next = model(context)
    context += next
    emit(next)

That's it. Every capability is built on this loop.

Kontext-fönstret är viktigt att förstå — det är allt modellen "ser" just nu. Hela konversationen, alla filer den läst, alla verktygssvar. 1 miljon tokens är ungefär 3000 sidor text. Det räcker för att lägga in hela vår kodbas i ett enda anrop. Det här är en av de stora förändringarna senaste året — förr fick man bara skicka 4000 tokens. Pratet om "prediction loop" — visa kodboxen. Det är bokstavligen vad en LLM är på lägsta nivå. Allt det fancy är byggt ovanpå den loopen.

What LLMs are good at

  • Fluent natural language — in any language
  • Translation between representations (code ↔ prose ↔ data)
  • Pattern matching across huge amounts of context
  • Tedious work that humans hate: boilerplate, refactors, glue
  • "Knowing a little about a lot" — broad shallow recall
Det här är inte uttömmande. Poängen är: LLMs är bra på saker som handlar om transformation och igenkänning, inte uppfinning. Konkret för oss: refaktorering, glue-kod, att skriva tester, översätta mellan format (JSON → TypeScript-typer, API-spec → klientkod), dokumentation som matchar koden. Det de är BÄST på är saker vi tycker är trist. Det är därför det är värt så mycket.

What LLMs are bad at

  • Hallucination — confident, plausible, wrong
  • Precise arithmetic and counting
  • Knowing what they don't know
  • True long-horizon planning without scaffolding
  • Anything genuinely novel — they interpolate, they don't invent
Most failure modes are shapes of these. Design around them.
Hallucination — påhittade API:er, påhittade funktionsnamn, "den här biblioteket har en X()" — nej det har det inte. Vanligaste och mest farliga felet. "Vet inte vad den inte vet" — den kommer aldrig säga "jag är osäker" om man inte tvingar den. Den svarar alltid självsäkert. Långhorisont-planering — en agent som ska fixa 50 saker tappar tråden. Lösningen är att dela upp i mindre steg och ge feedback (tester, typer). Nytt — om du försöker få den att uppfinna en helt ny algoritm är det fel verktyg. Den interpolerar mellan saker den sett. Designprincipen: bygg system där det inte spelar någon roll om den hallucinerar — för testen fångar det, eller verktyget gör det inte möjligt.

The shift that made agents possible

  • Tool use — the model can emit "call this function with these args"
  • Larger context — fit whole codebases, not just snippets
  • Reasoning models — think before answering, self-critique
  • Reliability — instruction-following finally works well enough to chain

The model didn't get smarter overnight. It got usable in a loop.

Det här är viktigt: agenter blev möjliga inte för att modellerna blev "smartare" i någon mystisk mening. Fyra konkreta saker hände. Tool use: modellen kan nu strukturerat säga "kör den här funktionen med de här argumenten". Det betyder att den kan läsa filer, köra tester, anropa API:er. Större kontext: tidigare fick man inte plats med kodbasen. Nu får man det. Reasoning: modellerna tänker först, svarar sedan. Det minskar hallucinationer dramatiskt. Reliability: instruktionsföljande blev bra nog för att kedja 50 steg utan att tappa det. Bottom line — det är inte ett quantum leap i intelligens. Det är att modellen blev pålitlig nog att sätta in i en loop.

Part 2

From LLM to agent

Nu till det intressanta. Vad är skillnaden mellan att fråga ChatGPT och att låta Claude Code jobba i din kodbas.

Chatbot vs. agent

ChatbotAgent
One question, one answerA goal, many steps
You driveIt drives
Text in, text outReads files, runs commands, calls APIs
You evaluate the answerIt evaluates its own work, retries, replans
StatelessMaintains state across a session
Den mest fundamentala förändringen är vem som driver. Med en chatbot är du föraren — du frågar, den svarar, du frågar igen. Med en agent säger du målet och den driver — den läser filer, kör tester, ändrar saker, kollar om det funkade, försöker igen. Det betyder också att du kan starta något och gå iväg. Det är en stor mental shift. Fråga publiken: hur många här har faktiskt suttit och låtit en agent jobba i 10+ minuter utan att avbryta? Hur kändes det? Tillit-frågan börjar redan här.

The agent loop

  ┌──────────────┐
  │   PERCEIVE   │  read files, run tests, fetch web
  └──────┬───────┘
         ▼
  ┌──────────────┐
  │    REASON    │  what does this mean? what next?
  └──────┬───────┘
         ▼
  ┌──────────────┐
  │     ACT      │  edit code, run command, call tool
  └──────┬───────┘
         ▼
  ┌──────────────┐
  │   OBSERVE    │  did it work? what changed?
  └──────┬───────┘
         └──► back to PERCEIVE

Everything else — Claude Code, Cursor, Devin, your own scripts — is this loop with different tools bolted on.

Avmystifiera. Alla agenter, hur fancy de än marknadsförs, är varianter av den här loopen. Skillnaden mellan en bra och en dålig agent är: vilka verktyg den har, hur bra observationer den får (tester, typer, lint), och hur den hanterar fel. Det viktiga för oss: vi kan bygga egna agenter. Det är inte rocket science. Kan vi koppla en LLM till våra verktyg har vi en agent.

What turns a model into an agent

  • Tools — file IO, shell, web, MCP servers, custom APIs
  • A scaffold — system prompt, memory, the loop itself
  • Permissions — what it can do without asking
  • Feedback signals — test results, type errors, linters, screenshots
  • A stopping condition — "task done" or "give up and ask"
De här fem sakerna är vad du designar när du sätter upp en agent. Inte modellen — det är fixt val. Men allt annat är design. Tools — vad får den göra. Bara läsa? Köra shell? Pusha kod? Scaffold — system prompt, CLAUDE.md, hur den minns över tid. Permissions — vad får den göra utan att fråga. För risky är det viktigt att den frågar först. Feedback signals — det här är där våra investeringar i tester/typer/lint betalar tillbaka 10x. En agent utan signaler driver i sidled. Stop condition — när är den klar? När ska den ge upp? Det här missar folk ofta.

The tools landscape (today)

IDE-embedded

  • Cursor
  • GitHub Copilot (Agent mode)
  • Windsurf
  • JetBrains AI

CLI / autonomous

  • Claude Code (CLI + web)
  • Codex / OpenAI agents
  • Devin
  • Aider

Different surfaces, same loop. Pick the one that fits your workflow.

Det är ett snabbt rörligt landskap. Listan stämmer idag, kanske inte om sex månader. IDE-embedded — du sitter kvar i din editor, AI:n är en sidofunktion. Lägre tröskel. CLI / autonomous — du startar något och låter det jobba. Mer kraft, mer tillit krävs. Min rekommendation: välj ETT verktyg och bli bra på det. Kontextväxling mellan tre olika AI-tools är värre än att bara använda ett. Vi i teamet bör konvergera på en eller två — det gör att vi kan dela prompts, patterns, lärdomar.

Part 3

Agentic AI in our organisation

Nu det praktiska. Vad gör vi konkret med det här på Sensative.

Where it fits in our work

  • Feature implementation from a spec or ticket
  • Bug triage and reproduction
  • Refactors and migrations (framework upgrades, API renames)
  • Test writing — especially edge cases
  • Documentation that actually matches the code
  • On-call: log analysis, incident summary, first-line response
  • Code review (more on this in Part 4)
Lista konkreta exempel från vår vardag. Ta gärna 2–3 från publiken: "vilka av era uppgifter senaste veckan skulle agenter kunnat ta?" Den dolda vinnaren här är test-skrivande. Det är något människor är dåliga på (trist, edge cases missas) som AI är väldigt bra på. On-call är också undervärderat. AI som första-läser loggar och föreslår orsak sparar mycket nattsömn.

The effective workflow

  1. Spec — what does done look like? Write it down.
  2. Plan — let the agent propose. Review before code is written.
  3. Implement — small, verifiable steps. Tests as you go.
  4. Verify — run it. Type-check, lint, test, and actually use the feature.
  5. Review — diff is the source of truth. Read it.
  6. Ship — commit, push, PR. Keep the agent in the loop on CI failures.
Det här är det sätt jag skulle vilja att vi jobbar. Det är inte mer komplicerat än så här. Step 1 — Spec. Den vanligaste anledningen till att AI:n gör fel är att vi var luddiga. "Done" måste vara konkret. Step 2 — Plan. Be agenten skriva en plan FÖRST, granska den, sen koda. Sparar enormt mycket tid jämfört med att fixa fel halvvägs in. Step 4 — Verify. Köra app:en. Inte bara tester. Tester verifierar kodkorrekthet, inte feature-korrekthet. Step 5 — Review. Diff:en är sanningen. Läs den. Allt agenten skriver i sammanfattning är "vad jag tänkte göra", inte "vad jag faktiskt gjorde".

Patterns that work

  • Small, well-scoped tasks — one ticket, not one quarter
  • Tight feedback loops — tests, types, linters wired up
  • Parallel agents — independent tasks in independent worktrees
  • "Trust but verify" — read the diff, run the app
  • Explicit context — CLAUDE.md, AGENTS.md, READMEs the agent will read
  • Hooks & MCP — let the agent reach your real systems
Parallel agents — den här är värd att stanna vid. Du kan starta tre agenter på tre oberoende tasks samtidigt, gå och fika, kolla diffs. Det är en av de största produktivitetsvinsterna. CLAUDE.md / AGENTS.md — om du bara gör EN sak i dina repon, gör den. Skriv ner: hur du kör tester, hur du kör appen, var koden ligger, vilka konventioner som gäller. Den filen är agentens onboarding. MCP — Model Context Protocol — låter agenten prata med Jira, Slack, GitHub, vad som helst. Är det vi inte utnyttjar tillräckligt än.

Patterns that fail

  • "Build me an app" — too vague, no feedback signal
  • Skipping the plan step on anything non-trivial
  • Approving diffs without reading them
  • Letting the agent invent abstractions for hypothetical futures
  • No tests, no types, no lint → no signal → drift
  • Treating it as autocomplete when it's actually a junior dev — or vice versa
De här är felen jag ser oftast. Inklusive hos mig själv. "Bygg en app" funkar inte. Det är som att säga åt en junior developer "fixa det" — du kommer få nåt, men inte det du ville. Diffs utan att läsa — den vanligaste anledningen till att AI-kod är dålig i kodbaser. Det är inte AI:n som gjort fel. Det är att ingen sa nej. Sista punkten — kalibrera förväntningar. Det är inte autocomplete (smartare än så). Det är inte heller en magisk full-stack dev (sämre än så). Det är en junior med encyclopedisk kunskap men noll omdöme. Behandla det därefter.

What changes for us as developers

Less of

  • Boilerplate
  • Looking up syntax
  • First-draft code
  • Migration grunt work

More of

  • Specification
  • Reviewing
  • System design
  • Judgement calls
  • Knowing why, not just how

The skill shifts from typing code to directing it.

Den här slidens budskap: din värde-add som developer flyttar uppåt i abstraktionsstegen. Det är inte att vi blir överflödiga. Det är att den lägsta nivån — att knappa kod — slutar vara där värdet sitter. Det betyder att junior-rollen förändras. Hur lär man sig om man aldrig behöver skriva boilerplate? Ärlig fråga. Värd att diskutera. För seniorer är det här mest en lättnad. De saker som är jobbiga försvinner. Det som är roligt — design, judgement — blir mer av jobbet.

What we should do — concretely

  • Pick one agent surface per developer (don't context-switch tools)
  • Wire up our test/lint/type pipelines so the agent gets fast feedback
  • Write a project CLAUDE.md / AGENTS.md per repo
  • Use MCP / GitHub Actions to give agents access to issues, CI, deployments
  • Share prompts and patterns that work — internal cookbook
  • Measure: what did we ship, what regressed, what was reverted
Det här är actionables. Om jag bara fick välja tre — det är 1, 3 och 5. Verktyget per dev — för att vi ska kunna dela tips måste vi prata samma språk. CLAUDE.md per repo — billigaste och högst impact-investeringen. Internal cookbook — vi ska INTE alla lära oss samma saker individuellt. Skapa en delad plats för "så här fick jag agent X att göra Y bra". Mätning — det här är där vi behöver vara disciplinerade. Annars vet vi inte om det här faktiskt funkar. Spåra: shippad funktionalitet, regressions, reverterad kod.

Part 4

Code review

Do we still need humans for it?

Det här är min favoritdel. Provokativ med flit. Vi går igenom argumentet, vänder på det, och landar någonstans i mitten. Tryck B här om du vill blanka skärmen och starta med frågan rakt ut: "behöver vi människor i code review längre?" Samla 2–3 åsikter innan du går vidare.

The compiler argument

Nobody reviews how GCC arranges instructions in the binary.
Nobody diffs the JIT output.
We trust the toolchain.

If an AI writes code that passes tests, types, lint, security scans, and behaves correctly in production — is reviewing it any different from reviewing assembly?

Läs blockquoten högt. Pausa. Säg: "Det här är inte en halmgubbe. Det är en riktig fråga. Vi gör samma sak på flera lager redan — vi reviewar inte vad webpack spottar ut, vi reviewar inte vad TypeScript-compilern genererar, vi reviewar inte Linux schemaläggarens beslut." Vänta. Låt publiken kanske invända. Sen — "okej, men håller analogin?" Det är vad nästa slide reder ut.

What is code review actually for?

  • Correctness — does it do the thing?
  • Safety — does it break other things?
  • Maintainability — can the next person read it?
  • Architectural fit — does it belong here, like this?
  • Knowledge sharing — does the team learn the change happened?
  • Accountability — who said yes?

Only the first two are verifiable. The rest are judgement.

Fråga publiken innan du visar listan: "vad är code review egentligen till för?" Samla några svar. Förmodligen får du "fånga buggar", "lära nya patterns", "dela kunskap". Visa listan. Poängen: vi har slagit ihop sex olika syften till en aktivitet. AI är jättebra på de första två. På de andra fyra är det inte alls säkert. Den underliggande insikten — kanske ska vi separera dem. Olika typer av review för olika syften.

The compiler analogy doesn't quite hold

  • A compiler is deterministic. An LLM is not.
  • A compiler has a spec. An LLM has training data and a prompt.
  • A compiler's output is read by machines. Our source code is read by humans — and by the next agent.
  • Compiler bugs are rare, reproducible, and shared across the industry. LLM bugs are common, non-reproducible, and yours alone.

But the analogy is useful — it points at where the line moves.

Nu vänder vi argumentet. Kompilator-analogin är frestande men den haltar. Determinism — kompilator + samma input ger alltid samma output. LLM + samma prompt ger olika output. Det enda enskilt största skillnaden. Spec — GCC har en ISO-standard. LLM har en blackbox av träningsdata. Källkod läses av människor — det är poängen med källkod. Maskinkod läses av maskiner. Det är inte samma sak. Compiler-buggar är reproducerbara och delade — när GCC har en bugg fixas den av alla. LLM-buggar är just dina. Men håll fast vid: analogin är inte värdelös. Den pekar mot ATT linjen flyttar — bara inte ända ner till noll review.

"AI can't be trusted" — can a human?

  • Humans hallucinate too — we call it "I was sure that was right"
  • Humans skim diffs, rubber-stamp, miss the obvious
  • Humans have bad days, deadlines, biases
  • Humans don't read every file the change touches

The honest question isn't "can we trust AI?" — it's "compared to what?"

Det här är min favoritslide. Vänd frågan tillbaka. Hur många här har approvat en PR utan att verkligen läsa diffen? *Vänta. Räcker upp handen själv om det är sant.* Hur många har missat ett tydligt fel i en review? Hur många har varit den som skickade in det felet? Människor är inte heller en gold standard. Vi är bara den standard vi vant oss vid. Linjen: "AI är inte perfekt — men jämfört med en trött människa som granskar PR fem på fredag eftermiddag är den inte värre. Ibland bättre."

Where AI review beats human review

  • Never tired, never skimming
  • Reads every file the diff touches, and the call sites
  • Consistent — same rules every time, no politics
  • Cheap enough to run on every commit, not just on PR
  • Multi-agent: ten reviewers in parallel for the cost of coffee
  • Catches the boring bugs humans miss because they're boring
Konsistens är underskattat. En människa kan ge olika feedback olika dagar, beroende på dagsform. AI ger samma feedback varje gång. "Cheap enough to run on every commit" — det här är en game changer. Vi har alltid haft code review som flaskhals för att den var dyr. Nu är den billig. Multi-agent — varför stanna vid en reviewer? Kör tre med olika fokus: en på säkerhet, en på korrekthet, en på maintainability. Triangulering.

Where humans still win

  • Intent — "is this what the customer actually wanted?"
  • Architecture — "should this even exist?"
  • Politics & ownership — "whose system is this?"
  • Novel risk — "we've never done X before; is this safe?"
  • Accountability — someone signs the change
  • Tacit context — the things nobody wrote down
Intent — AI vet vad koden gör. Det vet inte vad användaren ville. Det är fortfarande vårt jobb. Architecture — "ska den här klassen ens existera?" Det är en helhetsfråga som kräver kontext om var vi är på väg. Accountability — när nåt går fel i produktion behöver det finnas en människa som sa "ja, det här går vi med på". Det är inte tekniskt — det är organisatoriskt. Tacit context — alla saker vi vet om vår kund, vår historik, våra konstigheter, som aldrig skrevs ner. Det är vår orättvisa fördel.

A new model for code review

┌───────────────────────────────────────────────────┐
│  AI: every commit, full diff, every rule          │
│      → correctness, security, style, regressions  │
└────────────────────┬──────────────────────────────┘
                     ▼
┌───────────────────────────────────────────────────┐
│  Human: the PR, the architectural decisions       │
│      → intent, fit, accountability                │
└───────────────────────────────────────────────────┘

Humans review less, but the review they do is higher value.

Två lager. AI på commit-nivå — fångar buggar, säkerhet, stil. Snabbt, billigt, alltid. Människor på PR-nivå — fokuserar på "är det här rätt sak att göra över huvud taget". Det här är inte att människor reviewar mindre. Det är att de reviewar SMARTARE. Mindre tid på "du missade en semikolon", mer tid på "har vi tänkt på hur det här interagerar med systemet vi byggde i fjol?"

What this looks like in practice

  • AI review runs on every push — comments inline before a human looks
  • Author addresses AI findings before requesting human review
  • Human reviewer focuses on the "why this, why now" questions
  • For low-risk PRs (small diffs, well-tested code) — AI approval may be enough
  • For high-risk PRs — two AI reviewers + a human, every time
  • Post-merge: AI watches production for the regressions humans miss
Konkret förslag. Det här kan vi börja med imorgon. "Author addresses AI findings först" — det här är avgörande. Annars sitter människan och säger samma sak som AI redan sagt. Slöseri. "Low-risk PRs" — vi behöver definiera vad det är. Storlek på diff, område i kodbasen, finns det tester. Risknivå styr nivå av review. "Post-merge AI watching prod" — det här är framtid. Men det är där det är på väg. AI som kontinuerligt övervakar för regressions och föreslår fix.

The uncomfortable conclusion

We will keep human code review.
But we will do less of it,
and the parts we keep will be the parts machines can't do —
judgement, intent, and accountability.

The reviewer of 2027 spends more time asking "should we?" and less time spotting off-by-one errors.

Läs blockquoten långsamt. Pausa. Det här är inte ett "AI tar våra jobb"-budskap. Det är ett "AI tar de tråkiga delarna av våra jobb"-budskap. De delarna vi inte ville göra ändå. Frågan "should we?" är en högre värde-fråga än "did you typo this?". Vi flyttar uppåt. Övergång till diskussionen: "Det här är min syn. Den är inte huggen i sten. Vad tänker ni?"

Part 5

Discussion

Öppna golvet. Du kan visa nästa slide med frågor som seed, eller låta diskussionen flöda fritt först. Om det blir tyst — peka på en specifik person med "du jobbar mest med X, hur skulle det här påverka det?"

Questions worth chewing on

  • Which tasks in your daily work would you give to an agent tomorrow?
  • What would have to be true for you to merge an AI-only-reviewed PR?
  • What does our team's CLAUDE.md need to say?
  • If reviewing becomes the bottleneck — do we hire more reviewers, or more agents?
  • What's the failure mode we're most afraid of — and how would we notice?
Fem frågor. Du behöver inte gå igenom alla — välj de som triggar mest engagemang. Den andra frågan — "what would have to be true" — är den mest produktiva. Den tvingar folk att bli konkreta om sina tvivel. Sista frågan — failure mode — är där rädslorna kommer fram. Bra ställe att avsluta så vi inte gick hem på en överoptimistisk ton.

Thank you

Questions, pushback, war stories — all welcome.
