Part 1

LLMs — getting on the same page

Snabbt genom det här. De flesta i rummet har använt ChatGPT eller Claude. Men det är värt att vara explicit om vad det faktiskt är — för det förklarar både vad det är bra på och var det kommer fela.

What an LLM actually is

  • A function: tokens → next token probability
  • Trained on enormous corpora of text + code
  • No memory between calls. No database lookup. No internet (by default).
  • It is not retrieving answers — it is generating them
If you remember one thing: it is a very fast, very fluent pattern completer.
Det viktiga: modellen "vet" ingenting. Den genererar det mest sannolika nästa token givet kontexten. När den verkar minnas något — så har den fått det matat till sig i prompten eller via ett verktyg. Det finns ingen "minnesbank" inuti. Det här förklarar varför den kan hitta på (hallucinera): att hitta på och att svara rätt är samma operation för modellen. Den vet inte skillnaden.

Where LLMs help — and where they hurt

Good at

  • Fluent text in any language
  • Translation: code ↔ prose ↔ data
  • Pattern matching across huge context
  • Tedious work: boilerplate, refactors, glue
  • Broad shallow recall

Bad at

  • Hallucination — confident, plausible, wrong
  • Precise arithmetic & counting
  • Knowing what they don't know
  • Long-horizon planning without scaffolding
  • Anything genuinely novel

Design around the weaknesses — most failure modes are shapes of these.

Snabb genomgång av båda kolumnerna — säg poängen: bra på transformation, dåligt på uppfinning. Hallucination är det enskilt farligaste — påhittade API:er, påhittade funktionsnamn. Vanligaste och mest farliga felet. Designprincipen: bygg system där det inte spelar någon roll om den hallucinerar — testen fångar det, eller verktyget gör det inte möjligt. Det de är BÄST på är saker vi tycker är trist. Det är därför det är värt så mycket.

Part 2

From LLM to agent

Nu till det intressanta. Vad är skillnaden mellan att fråga ChatGPT och att låta Claude Code jobba i din kodbas.

Chatbot vs. agent

ChatbotAgent
One question, one answerA goal, many steps
You driveIt drives
Text in, text outReads files, runs commands, calls APIs
You evaluate the answerIt evaluates its own work, retries, replans
StatelessMaintains state across a session
Den mest fundamentala förändringen är vem som driver. Med en chatbot är du föraren — du frågar, den svarar, du frågar igen. Med en agent säger du målet och den driver — den läser filer, kör tester, ändrar saker, kollar om det funkade, försöker igen. Det betyder också att du kan starta något och gå iväg. Det är en stor mental shift. Fråga publiken: hur många här har faktiskt suttit och låtit en agent jobba i 10+ minuter utan att avbryta? Hur kändes det? Tillit-frågan börjar redan här.

The agent loop

Claude Code is this loop with shell, file IO, and git bolted on.

Avmystifiera. Alla agenter, hur fancy de än marknadsförs, är varianter av den här loopen. Skillnaden mellan en bra och en dålig agent är: vilka verktyg den har, hur bra observationer den får (tester, typer, lint), och hur den hanterar fel. Det viktiga för oss: vi kan bygga egna agenter. Det är inte rocket science. Kan vi koppla en LLM till våra verktyg har vi en agent.

Part 3

Agentic AI in our organisation

Nu det praktiska. Vad gör vi konkret med det här på Sensative. Säg: "i den här delen kommer vi också göra en live-demo — jag startar tre agenter parallellt och låter dem bygga en liten sensor-dashboard medan vi pratar. Det är där bilden av vad det här ÄR blir konkret."

The effective workflow

  1. Spec — what does done look like? Write it down.
  2. Plan — let the agent propose. Review before code is written.
  3. Implement — small, verifiable steps. Tests as you go.
  4. Verify — run it. Type-check, lint, test, and actually use the feature.
  5. Review — diff is the source of truth. Read it.
  6. Ship — commit, push, PR. Keep the agent in the loop on CI failures.
Det här är det sätt jag skulle vilja att vi jobbar. Det är inte mer komplicerat än så här. Step 1 — Spec. Den vanligaste anledningen till att AI:n gör fel är att vi var luddiga. "Done" måste vara konkret. Step 2 — Plan. Be agenten skriva en plan FÖRST, granska den, sen koda. Sparar enormt mycket tid jämfört med att fixa fel halvvägs in. Step 4 — Verify. Köra app:en. Inte bara tester. Tester verifierar kodkorrekthet, inte feature-korrekthet. Step 5 — Review. Diff:en är sanningen. Läs den. Allt agenten skriver i sammanfattning är "vad jag tänkte göra", inte "vad jag faktiskt gjorde".

Part 4

Code review

Do we still need humans for it?

Det här är min favoritdel. Provokativ med flit. Vi går igenom argumentet, vänder på det, och landar någonstans i mitten. Tryck B här om du vill blanka skärmen och starta med frågan rakt ut: "behöver vi människor i code review längre?" Samla 2–3 åsikter innan du går vidare.

The compiler argument

Nobody reviews how GCC arranges instructions in the binary.
Nobody diffs the JIT output.
We trust the toolchain.

If an AI writes code that passes tests, types, lint, security scans, and behaves correctly in production — is reviewing it any different from reviewing assembly?

Läs blockquoten högt. Pausa. Säg: "Det här är inte en halmgubbe. Det är en riktig fråga. Vi gör samma sak på flera lager redan — vi reviewar inte vad webpack spottar ut, vi reviewar inte vad TypeScript-compilern genererar, vi reviewar inte Linux schemaläggarens beslut." Vänta. Låt publiken kanske invända. Sen — "okej, men håller analogin?" Det är vad nästa slide reder ut.

What is code review actually for?

  • Correctness — does it do the thing?
  • Safety — does it break other things?
  • Maintainability — can the next person read it?
  • Architectural fit — does it belong here, like this?
  • Knowledge sharing — does the team learn the change happened?
  • Accountability — who said yes?

Only the first two are verifiable. The rest are judgement.

Fråga publiken innan du visar listan: "vad är code review egentligen till för?" Samla några svar. Förmodligen får du "fånga buggar", "lära nya patterns", "dela kunskap". Visa listan. Poängen: vi har slagit ihop sex olika syften till en aktivitet. AI är jättebra på de första två. På de andra fyra är det inte alls säkert. Den underliggande insikten — kanske ska vi separera dem. Olika typer av review för olika syften.

The compiler analogy doesn't quite hold

  • A compiler is deterministic. An LLM is not.
  • A compiler has a spec. An LLM has training data and a prompt.
  • A compiler's output is read by machines. Our source code is read by humans — and by the next agent.
  • Compiler bugs are rare, reproducible, and shared across the industry. LLM bugs are common, non-reproducible, and yours alone.

But the analogy is useful — it points at where the line moves.

Nu vänder vi argumentet. Kompilator-analogin är frestande men den haltar. Determinism — kompilator + samma input ger alltid samma output. LLM + samma prompt ger olika output. Det enda enskilt största skillnaden. Spec — GCC har en ISO-standard. LLM har en blackbox av träningsdata. Källkod läses av människor — det är poängen med källkod. Maskinkod läses av maskiner. Det är inte samma sak. Compiler-buggar är reproducerbara och delade — när GCC har en bugg fixas den av alla. LLM-buggar är just dina. Men håll fast vid: analogin är inte värdelös. Den pekar mot ATT linjen flyttar — bara inte ända ner till noll review.

"AI can't be trusted" — can a human?

  • Humans hallucinate too — we call it "I was sure that was right"
  • Humans skim diffs, rubber-stamp, miss the obvious
  • Humans have bad days, deadlines, biases
  • Humans don't read every file the change touches

The honest question isn't "can we trust AI?" — it's "compared to what?"

Det här är min favoritslide. Vänd frågan tillbaka. Hur många här har approvat en PR utan att verkligen läsa diffen? *Vänta. Räcker upp handen själv om det är sant.* Hur många har missat ett tydligt fel i en review? Hur många har varit den som skickade in det felet? Människor är inte heller en gold standard. Vi är bara den standard vi vant oss vid. Linjen: "AI är inte perfekt — men jämfört med en trött människa som granskar PR fem på fredag eftermiddag är den inte värre. Ibland bättre."

Who's better at what?

AI wins onHumans still win on
Never tired, never skimmingIntent — what did the customer want?
Reads every file the diff touchesArchitecture — should this exist?
Consistent — no bad days, no politicsNovel risk — we've never done X
Cheap on every commit, not just PRAccountability — someone signs the change
Multi-agent: ten reviewers in parallelTacit context — things nobody wrote down
Gå igenom raderna parvis. AI:s styrkor är skala och konsistens. Människans styrkor är kontext och ansvar. Konsistens är underskattat — en människa kan ge olika feedback olika dagar, AI ger samma varje gång. "Cheap on every commit" — det är game changern. Code review var flaskhals för att det var dyrt. Nu är det billigt. Accountability — när nåt går fel i produktion behöver det finnas en människa som sa "ja". Det är inte tekniskt — det är organisatoriskt.

A new model for code review

Humans review less, but the review they do is higher value.

Två lager. AI på commit-nivå — fångar buggar, säkerhet, stil. Snabbt, billigt, alltid. Människor på PR-nivå — fokuserar på "är det här rätt sak att göra över huvud taget". Det här är inte att människor reviewar mindre. Det är att de reviewar SMARTARE. Mindre tid på "du missade en semikolon", mer tid på "har vi tänkt på hur det här interagerar med systemet vi byggde i fjol?"

The uncomfortable conclusion

We will keep human code review.
But we will do less of it,
and the parts we keep will be the parts machines can't do —
judgement, intent, and accountability.

The reviewer of 2027 spends more time asking "should we?" and less time spotting off-by-one errors.

Läs blockquoten långsamt. Pausa. Det här är inte ett "AI tar våra jobb"-budskap. Det är ett "AI tar de tråkiga delarna av våra jobb"-budskap. De delarna vi inte ville göra ändå. Frågan "should we?" är en högre värde-fråga än "did you typo this?". Vi flyttar uppåt. Övergång till diskussionen: "Det här är min syn. Den är inte huggen i sten. Vad tänker ni?"

Part 5

Your turn — hands-on

Detta är skiftet — från "lyssna på mig" till "prova själv". Säg: "förmiddagens hela poäng var att ge er konceptuell grund. Det är inte lyssnandet som lär er det här — det är att göra. Nästa tre timmar är ni föraren." Räkna med 5 min energi-paus efter Part 4 innan du går in i den här delen.

The brief

  • 4–5 teams, 2–4 people each.
  • Phase 1 — team builds the foundation together (~30 min)
  • Phase 2 — each person works solo from their own laptop, opens a PR (~2 h, lunch in the middle)
  • Phase 3 — review each other's PRs, integrate, ship (~30 min)
  • By 14:00 — a working app on main, with a PR from every member.

This is what Claude in a real team looks like. Not one driver — many drivers, one repo.

Det här är det nya formatet. Säg det tydligt: "första halvtimmen bygger ni TILLSAMMANS. Sen splittar ni — alla på sin egen laptop, sina egna PRs." Poängen: visa att Claude funkar i ett riktigt team, inte bara solo. "By 14:00 — a PR from every member" — gör det till en deliverable. Det är där de upptäcker att de måste planera så uppgifterna är ungefär lika stora.

The flow

Gå igenom diagrammet vänster till höger. Det är arkitekturen för hela hands-on-dagen. Phase 1 är där grupperna lägger grunden — projektval, CLAUDE.md, feature-uppdelning. Phase 2 är där det blir spännande — fyra personer som JOBBAR PARALLELLT med fyra agenter, fyra branches, fyra PRs som rullar in i repot samtidigt. Phase 3 är där de blir lite verkliga konsekvenser av AI-team-utveckling — krockar mellan PRs, AI som reviewar AI:s kod, mänskliga val om vad som faktiskt ska in.

Pick a project

Starter ideas

  • A · CLI: git-tldr — summarize last N commits in plain English
  • B · Tiny issue tracker — kanban with three columns and drag-drop
  • C · Expense splitter — "I paid X for the dinner, who owes what?"
  • D · Pomodoro timer with team sync — websockets demo
  • E · Public-API mashup — pick an API, transform, display nicely

Or freestyle

Something useful for your daily work. Internal tool. Personal scratch app. Anything you've wanted but never had time to build.

Pick something that can be cleanly split into 3–4 independent features — one per team member.

Viktigt tillägg jämfört med solo-formatet: projektet måste kunna SPLITTAS i 3-4 oberoende features. Annars blockerar folk varandra. Hjälp grupperna med splittningen om de fastnar. T.ex. för kanban: en bygger backend-API, en bygger drag-drop, en bygger persistence, en bygger styling. Säg explicit: undvik features som måste byggas i sekvens. Allas PRs ska kunna gå parallellt.

Phase 1 — Team kickoff (30 min)

  1. Pick a project (5 min — don't overthink it)
  2. One person creates a GitHub repo, adds everyone as collaborators
  3. Decide on stack together. Keep it simple.
  4. Scaffold the empty project — together, screen-shared. One Claude session does this.
  5. Write the CLAUDE.md as a team — stack, run commands, conventions, code style
  6. Split the work into 3–4 features. Open one GitHub issue per feature. Assign one to each member.
  7. Push main. Everyone clones to their own laptop.

CLAUDE.md is the contract. Once it's pushed, no one diverges from it.

Phase 1 är det viktigaste 30 min-passet hela dagen. Om det blir slarvigt här straffar det sig under Phase 2 och 3. Var aktiv som facilitator här. Gå runt och kolla att varje grupp har: en repo, en CLAUDE.md, 3-4 issues, alla har clonat. "CLAUDE.md is the contract" — säg det två gånger. Det är där team-disciplin börjar.

Phase 2 — Solo work (~2 h, lunch included)

  • Branch: feature/<your-name>-<short-thing>
  • Open Claude Code on your laptop. Point it at your assigned issue.
  • Plan first. Ask the agent for a plan. Read it. Adjust. Then code.
  • Verify by running before you push.
  • Open a PR. Description: what, why, how to test.
  • While you wait for review — pick someone else's open PR and review it.

You will overlap. Don't panic — Claude is good at resolving its own merge conflicts.

Den här fasen är det de kommer prata om i månader efteråt. Det är där "wow, det funkar i team" -ögonblicket händer. Säg innan de börjar: "lunch är mitt i den här fasen. Det är OK att stänga laptopen och äta. Det är OK att tänka över maten." "Claude is good at resolving its own merge conflicts" — säg det med eftertryck. Många kommer få sin första konflikt och kommer instinktivt panika. Säg "be agenten lösa det. Den klarar det." Gå runt aktivt under den här fasen. Sitt 2 min hos varje person, lyssna på hur de promptar.

Phase 3 — Review and integrate (~30 min)

  1. Run /code-review (or @claude review this PR) on every open PR
  2. Each PR gets one teammate as human reviewer — not the author
  3. Discuss any AI findings the human reviewer disagrees with
  4. Merge in an order that minimises conflicts. Coordinate out loud.
  5. Pull main, run the integrated app. Does it work?
  6. If not — open a new PR (with Claude's help) to fix the integration

Watch what AI catches vs. what the human catches. That's the data point.

Den här fasen är där Part 4 (code review-diskussionen) blir konkret. Säg det till grupperna: "ni får nu se i praktiken vad vi pratade om — AI på commits, människa på PR." Sista bulleten är värdefull att diskutera i demon: "vad fångade AI:n som vi inte hade fångat? Vad fångade vi som AI:n missade?" Tiden är knapp — 30 min är inte mycket. Påminn dem 10 min innan att starta integrationen och inte hänga kvar i fler PRs.

Group demos

Du är nu i moderator-roll. Hålltider strikt — 5 min per grupp + 2 min frågor. Använd timer synligt så grupperna ser den.

Demo format — 5 minutes per team

  1. Run the integrated app — show what's on main (~1 min)
  2. Show your CLAUDE.md — the team contract (~30 s)
  3. Show your PR list — one per member, merged or open (~30 s)
  4. Spotlight one PR — walk through the prompts that built it (~1.5 min)
  5. One thing that went wrong — merge conflict, agent loop, miscommunication (~1 min)
  6. One thing you'd do differently next time (~30 s)

Process > product. We learn more from your PRs than your code.

Säg det här innan demos börjar så teamen vet exakt vad de ska visa. Punkt 3 (visa PR-listan) är där team-formatet syns. Alla ska ha en PR. Om någon inte har det — diskutera varför, ärligt. "Process > product" — det är den enda regeln som verkligen räknas idag.
